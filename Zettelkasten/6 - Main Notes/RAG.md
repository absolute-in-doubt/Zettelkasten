# RAG - Retrieval Augmented Generation

![[Pasted image 20260912165323.png]]



1. Chunking - разбиение исходной информации на маленькие кусочки. Retriever в последствии будет доставть информацию именно целыми чанками, поэтому они не должны быть большими.
	
	- Chunk - именно plain text

```
┌──────────────────────────────────────────────┐
│ Vector DB                                    │
├──────────────┬─────────────────┬─────────────┤
│ id           │ embedding       │ metadata    │
├──────────────┼─────────────────┼─────────────┤
│ chunk-001    │ [0.12, -0.43,..]│ source=...  │
│ chunk-002    │ [0.87,  0.11,..]│ source=...  │
│ chunk-003    │ [-0.21, 0.54,..]│ source=...  │
└──────────────┴─────────────────┴─────────────┘
```
- `id` — идентификатор чанка

- `embedding` — векторное представление текста. Это результат работы **Embedding Model**:
```
"Kafka consumer commits offsets..."
             ↓
       Embedding Model
             ↓
[0.123, -0.532, 0.871, ...]
```
Именно по этому вектору Vector DB делает similarity search.


- `metadata` - Дополнительные данные:

```json
{
  "source": "kafka.md",
  "section": "Consumer Groups",
  "chunkIndex": 4
}
```

> [!note]
> Вместе с `embedding` в векторной БД может храниться и сам `text`. 
> 
> Или же Vector DB может хранить только: `id`, `embedding`, `metadata`, сам текст лежит отдельно в другой БД.


#### Chank Overlapping

- **Chunk Overlap** - это количество символов ()или токенов, в зависимости от splitter-а), которое включается и в конец предыдущего чанка и в начало следующего. ~={orange}**Это помогает сохранить контекст между чанками**=~
	_Например, если `chunk_overlap = 100`, то последние 100 символов одного чанка появятся в начале следующего чанка._ 

![[Pasted image 20260912174217.png|376]]


> [!example]
> Оптимальнее всего при работе с большими текстами, такими например как, книги, новеллы и т.д., ставить `chunk_overlap = 20 - 100`.
