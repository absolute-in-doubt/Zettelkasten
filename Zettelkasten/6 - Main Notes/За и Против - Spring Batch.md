# За и Против - Spring Batch


**За**

- **Chunk-oriented processing «из коробки»**: read→process→write с транзакцией на чанк, а не на весь джоб — при падении посреди обработки не нужно откатывать/переделывать всё с нуля.
- **Restart с точки отказа.** `JobRepository` хранит состояние выполнения (какие chunk'и обработаны) — упавший на середине джоб продолжает, а не стартует заново. Критично именно для батчей с тысячами записей.
- **Skip/retry policy как конфигурация, а не ручной код.** Отказ по одному item (одна запись не прошла трансформацию) не роняет весь step — декларативно указывается, какие исключения skippable/retryable и лимиты.
- **Партиционирование/multi-threaded step** для горизонтального масштабирования объёма без смены модели программирования.
- **Готовые reader/writer** для JDBC, файлов и т.д.; экосистема Spring — минимальный порог входа для команды, уже сидящей на Spring Boot.
- **Метаданные выполнения из коробки** (время старта/финиша, число обработанных/skipped item'ов) — то, что иначе пришлось бы вести руками.

**Против**

- **Собственная схема метаданных** (`BATCH_JOB_*`, `BATCH_STEP_*`) — дополнительные таблицы, миграции, эксплуатационная поверхность в той же БД.
- **Модель программирования не бесплатна.** `ItemReader/ItemProcessor/ItemWriter/JobRepository/JobLauncher` — специфичная абстракция, которую нужно осваивать, даже если команда знает Spring; конфигурация flow (steps, decision points) многословна для нетривиальных сценариев.
- **Транзакционная модель заточена под JDBC-ресурсы.** Chunk commit предполагает транзакционный reader/writer; запись в Kafka не транзакционна в том же смысле — нужен кастомный `ItemWriter` (не сложно, но не «из коробки» бесшовно, особенно если нужна ровно одна публикация события на успешный chunk).
- **Синхронные вызовы внутри step (REST) требуют аккуратности** с интервалом commit — long-running item processing внутри chunk-транзакции может держать транзакцию БД открытой дольше желаемого.
- **Overkill для простых линейных джобов.** Если не нужен restart-from-checkpoint, skip/retry на уровне item и большой объём — обычный `@Scheduled` + свой код будет короче и понятнее без лишней абстракции.
- **Риск задвоения источника истины.** Если в домене уже есть собственные сущности со статусной моделью (как здесь `MigrationBatch`/`ReconciliationRecord`), легко получить два независимых трекера состояния выполнения — свой доменный и `JobRepository` — которые надо синхронизировать вручную или явно решить, какой из них авторитетный.

## Применительно к legacy-collection-migration-service

Да, стоит — но не целиком на весь сервис, а под два конкретных workload'а, которые по форме уже сейчас батчевые:

1. **Extraction → validation → transformation.** Это ровно chunk-oriented pipeline: read из Oracle read-реплики (`ItemReader`) → структурная валидация + семантическая трансформация (`ItemProcessor`, с skip policy на структурно невалидные записи, §4.2/§4.4 SDD) → write в Kafka (`ItemWriter` на `rop.migration.case.migrated`). Требование «частичный сбой трансформации не роняет батч» (§12 SDD) — это дословно skip-semantics Spring Batch, а не то, что стоит переизобретать руками.
2. **Ежедневная сверка.** Reader — дела из `CaseWatermark`, прошедшие фильтр покоя; processor — синхронный `GET` к `debt-case-service` + классификация; writer — `ReconciliationRecord` + условная публикация `mismatch-found`. Retry на transient-ошибки `GET` конфигурируется декларативно, а не собственным retry-кодом вокруг `RestClient`.

Оговорки:

- **Не делать `JobRepository` вторым источником истины.** Пусть он остаётся чисто инфраструктурной бухгалтерией для restart, а бизнес-факты (статус батча, `recordCount`, `mismatchCount`, история расхождений) как и спроектировано — в `MigrationBatch`/`ReconciliationRecord`. Не выставлять `JobRepository`-таблицы наружу через API отчётов.
- **Kafka-writer — кастомный**, штатного transactional item writer под Kafka в ванильном Spring Batch нет; писать его придётся самим (не сложно, но заложить в оценку).
- **Довод «сервис временный, не стоит вкладываться»** — не считаю решающим: команда и так на Spring Boot (см. `06_tech_stack`), Spring Batch — инкрементальное расширение знакомого стека, а не отдельная платформа вроде Airflow, так что стоимость входа ниже, чем кажется, а выгода (restart, skip, retry без ручного кода) окупается уже на объёме в десятки тысяч дел за проект.

Если бы объём был на порядок меньше и не было требования частичного skip/retry — я бы сказал «не берите Spring Batch, обычный `@Scheduled`-сервис проще». Но здесь оба требования (partial failure handling, restart без передела всего батча) уже явно заложены в SDD как функциональные — значит, вы либо пишете их руками, либо берёте библиотеку, которая это уже умеет. Я бы взял библиотеку.
