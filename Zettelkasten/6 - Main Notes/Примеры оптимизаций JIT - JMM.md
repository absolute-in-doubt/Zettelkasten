# Примеры оптимизаций JIT - JMM


> **C1 → быстро компилирует, делает простые оптимизации.**  
> **C2 → долго компилирует, глубоко анализирует код и агрессивно оптимизирует.**

Главное различие не в том, что C1 «плохой», а C2 «хороший», а в **стоимости анализа и глубине оптимизации**.

# 1. Что вообще делает JIT


Изначально данный код исполняется JVM через интерпретатор:

```java
for (int i = 0; i < 1_000_000; i++) {
    sum += array[i];
}
```

Когда JVM видит, что метод стал **hot**, она компилирует его в машинный код.

Например:

```java
int sum(int[] array) {
    int sum = 0;
	
    for (int i = 0; i < array.length; i++) {
        sum += array[i];
    }
	
    return sum;
}
```

JIT может превратить его в гораздо более эффективный машинный код.

~={orange}Но JIT должен решить:=~

> ~={orange}«Сколько времени я готов потратить на анализ этого метода, чтобы потом сэкономить время на его выполнении?»=~

Отсюда C1 и C2.

---

# 2. C1 — быстрые и относительно простые оптимизации

**C1 = Client Compiler.**

Его основная идея:

> **Быстро получить прилично оптимизированный машинный код.**

Он не хочет несколько миллисекунд анализировать сложные взаимосвязи в большом графе вызовов.

### Что запоминать про C1

|Оптимизация|C1|
|---|---|
|Constant folding|✅|
|Простое устранение dead code|✅|
|Простое упрощение выражений|✅|
|Inlining небольших методов|✅|
|Простые branch optimizations|✅|
|Простые loop optimizations|✅|
|Escape Analysis|❌ / существенно ограничено|
|Scalar Replacement|❌|
|Агрессивный interprocedural analysis|❌|
|Агрессивный inlining|❌|
|Сложная speculative optimization|❌|


> **C1 старается быстро оптимизировать локальный код.**

---

### Пример C1: constant folding

```java
int calculate() {
    return 10 * 20 + 5;
}
```

JIT может вычислить это заранее:

```java
return 205;
```

Вместо того чтобы выполнять:

```java
10 * 20
     ↓
   200
     ↓
 + 5
     ↓
   205
```

Это простая оптимизация.

---

### C1: inlining

Например:

```java
int square(int x) {
    return x * x;
}

int calculate(int x) {
    return square(x) + 10;
}
```

Вызов:

```java
square(x)
```

может быть встроен:

```java
return x * x + 10;
```

То есть JVM убирает overhead вызова метода и получает больше возможностей для последующих оптимизаций.

C1 умеет это делать, особенно для маленьких методов.

Но **C2 делает inlining гораздо агрессивнее**.

И это одна из самых важных вещей для понимания JIT.

---

# 3. C2 — глубокая оптимизация

**C2 = Server Compiler.**

Его философия:

> «Метод действительно горячий? Тогда я готов потратить больше CPU на анализ и получить максимально быстрый машинный код».

C2 анализирует не только отдельные инструкции, но и **взаимодействие методов, объектов, типов и control flow**.

---

# ~={red}Escape Analysis=~ - важная оптимизация

Вот здесь начинается одна из главных оптимизаций C2.

Допустим:

```java
class Point {
    int x;
    int y;
}

int calculate() {
    Point p = new Point();
    p.x = 10;
    p.y = 20;

    return p.x + p.y;
}
```

Наивно:

```java
new Point()
     ↓
heap allocation
     ↓
GC pressure
```

Но C2 может понять:

> `p` нигде не покидает метод.

Объект **не escape-ит**.

Поэтому JVM может вообще убрать allocation.

Получится концептуально:

```java
return 10 + 20;
```

или еще дальше:

```java
return 30;
```

Это уже совершенно другой уровень анализа.

---

### Scalar Replacement

~={red}Связан с Escape Analysis.
=~
Например:

```java
Point p = new Point();

p.x = 10;
p.y = 20;

return p.x + p.y;
```

Вместо объекта:

```
Point
 ├── x = 10
 └── y = 20
```

JIT может рассматривать его как отдельные значения:

```java
x = 10
y = 20
```

То есть объект физически вообще не создаётся.

Это называется **Scalar Replacement of Aggregates**.

Для разработчика это важно, потому что:

```java
new SomeSmallObject()
```

не всегда означает реальный allocation в heap в горячем оптимизированном коде.

---

### ~={orange}Агрессивный inlining=~

Представим:

```java
int process(Order order) {
    return calculatePrice(order);
}

int calculatePrice(Order order) {
    return order.getPrice() * 2;
}
```

C2 может построить примерно такую картину:

```java
process()
   ↓
calculatePrice()
   ↓
getPrice()
```

и встроить всё:

```java
return order.price * 2;
```

А после этого появляются новые возможности оптимизации.

Например:

```java
int process(Order order) {
    return calculatePrice(order) + calculateDiscount(order);
}
```

После inlining C2 может видеть всю цепочку вычислений и оптимизировать её целиком.

**Поэтому inlining — это не только оптимизация вызова.**

Он открывает дорогу другим оптимизациям.


---
### Dead Code Elimination

Например:

```java
int calculate() {
    int a = expensiveCalculation();
    int b = 10;

    return b;
}
```

Если C2 докажет, что результат:

```java
expensiveCalculation()
```

никуда не влияет и у метода нет наблюдаемого побочного эффекта, вычисление может быть удалено.

Концептуально:

```java
int calculate() {
    return 10;
}
```

---

### Loop optimization

Циклы — крайне важная область для JIT.

Например:

```java
for (int i = 0; i < array.length; i++) {
    sum += array[i];
}
```

C2 может применять различные оптимизации циклов:

- loop unrolling;
- оптимизацию условий;
- устранение некоторых проверок;
- оптимизацию инвариантов цикла;
- оптимизацию bounds checks в подходящих случаях;
- улучшение использования CPU registers.

#### Например loop unrolling

Было:

```java
for (int i = 0; i < 100; i++) {
    sum += array[i];
}
```

Концептуально может стать чем-то вроде:

```java
sum += array[0];
sum += array[1];
sum += array[2];
sum += array[3];
// ...
```

Это уменьшает overhead самого цикла и может улучшить использование CPU.

Не следует воспринимать это как буквальный гарантированный результат для каждого цикла — конкретное решение зависит от JVM и контекста.

---
### Bounds Check Elimination

Очень интересная для Java оптимизация.

Обычный доступ:

```java
array[i]
```

логически требует проверки:

```java
0 <= i < array.length
```

JVM должна защищать Java-программу от выхода за границы массива.

Но если JIT может доказать, что индекс всегда допустим:

```java
for (int i = 0; i < array.length; i++) {
    sum += array[i];
}
```

то повторяющуюся проверку можно оптимизировать.

Это особенно важно для производительности больших циклов.

---

### Branch optimization

Например:

```java
if (true) {
    doSomething();
} else {
    doSomethingElse();
}
```

Очевидно, что:

```java
doSomethingElse();
```

никогда не выполняется.

JIT может убрать недостижимую ветку.

Но C2 идёт дальше благодаря информации о runtime.


---
### Speculative optimization

Вот это особенно важно понимать.

Допустим:

```java
Animal animal = getAnimal();

animal.makeSound();
```

Теоретически:

```
Animal
 ├── Dog
 ├── Cat
 └── Cow
```

и JVM должна учитывать virtual dispatch.

Но JVM во время выполнения видит:

> «За последние миллионы вызовов здесь всегда был `Dog`.»

C2 может оптимизировать код, **предположив**, что здесь практически всегда `Dog`.

Тогда вместо полноценного virtual dispatch можно получить более прямой путь.

Если предположение нарушается, JVM может сделать **deoptimization** и вернуться к менее оптимизированному варианту.

Вот это одна из фундаментальных идей HotSpot:

> **JIT может оптимизировать код на основании информации, полученной во время выполнения.**

---

## 4. Где здесь Tiered Compilation

В современном HotSpot обычно используется **Tiered Compilation**.

Упрощённо:

```
Interpreter
     │
     ▼
    C1
     │
     ▼
    C2
```

Но технически есть несколько уровней компиляции:

```
Tier 0  → interpreter
Tier 1  → C1
Tier 2  → C1 + profiling
Tier 3  → C1 + profiling
Tier 4  → C2
```

Идея:

```
метод появился
     ↓
интерпретируется
     ↓
стал достаточно горячим
     ↓
C1 быстро компилирует
     ↓
продолжает собираться profiling information
     ↓
стал очень горячим
     ↓
C2 компилирует агрессивно
```

Это компромисс между:

**временем запуска**

и

**максимальной производительностью после прогрева**.

---

### 5. Что это значит для разработчика

Вот здесь знания о C1/C2 действительно становятся полезными.

**Не надо оптимизировать Java-код так, будто JVM — простой интерпретатор** Например, новичок может увидеть:

```java
private int square(int x) {
    return x * x;
}
```

и подумать:

> «Вызов метода дорогой, надо вручную убрать метод».

Не обязательно.

JIT может превратить:

```java
square(x)
```

в:

```java
x * x
```

посредством inlining.

Поэтому хороший Java-код часто можно писать **абстрактно и читаемо**, не жертвуя производительностью без необходимости.

---

### 6. Но нельзя рассчитывать на магию JIT

Вот обратная сторона.

Например, ты сделал очень сложную архитектуру:

```
Service
 ↓
Proxy
 ↓
Decorator
 ↓
Generic abstraction
 ↓
Reflection
 ↓
Dynamic proxy
 ↓
actual implementation
```

Иногда JIT сможет всё это хорошо оптимизировать.

Иногда — нет.

Особенно проблемными для оптимизации могут быть:

- reflection;
- динамические вызовы;
- непредсказуемый polymorphism;
- слишком большие методы;
- слишком сложный control flow;
- вызовы, которые невозможно inline;
- native calls;
- код с сильной зависимостью от runtime-состояния.

Поэтому **не стоит автоматически считать, что JIT уберёт любую абстракцию**.

---

### 7. Самое практичное применение — писать код, который легко оптимизировать

Например:

```java
int calculate(Order order) {
    return order.getPrice() * order.getQuantity();
}
```

Это очень удобный материал для JIT:

- маленький метод;
- простой control flow;
- предсказуемые типы;
- легко inline;
- легко оптимизировать дальше.

А вот:

```java
int calculate(Object value) {
    return ((SomeInterface) value).calculate();
}
```

может давать JVM меньше информации.

Не значит, что такой код плохой. Просто оптимизация может быть сложнее.

---

### 8. Escape Analysis полезно понимать при работе с объектами

Например:

```java
public int calculate() {
    Money money = new Money(100);
    return money.amount() * 2;
}
```

Не нужно автоматически думать:

> `new Money()` → обязательно allocation → GC.

В горячем коде C2 потенциально может доказать, что объект не escape-ит, и устранить allocation.

Но опять же:

> **Не программируй с предположением, что JVM гарантированно уберёт allocation.**

Проверяй benchmark/profiler, если это реально performance-critical место.

---

## 9. Особенно важно для микробенчмарков

Например:

```java
@Benchmark
public int test() {
    return 10 * 20;
}
```

JIT может сказать:

```java
10 * 20
   ↓
200
```

а затем понять, что результат вообще никуда не используется.

В итоге ты можешь измерять практически **ничего**.

Поэтому в JMH есть специальные механизмы вроде:

```
Blackhole
```

которые не позволяют JIT просто выкинуть вычисления.

Это прямое практическое следствие знания JIT.

---

## 10. Почему benchmark должен прогреваться

Если ты сразу запускаешь:

```
start application
↓
execute benchmark
↓
measure
```

ты можешь измерять:

```
Interpreter
+
C1 compilation
+
C2 compilation
+
JIT warmup
```

а не стабильную производительность оптимизированного кода.

Поэтому:

```
warmup
warmup
warmup
warmup
↓
C1
↓
C2
↓
steady state
↓
measurement
```

Именно поэтому для Java performance benchmarking используют **JMH**.

---

## 11. Deoptimization — ещё одна важная вещь

Допустим C2 решил:

```
Этот вызов всегда получает Dog.
```

и построил оптимизированный код.

Но потом пришёл:

```
Cat
```

JVM не обязана продолжать использовать неправильное предположение.

Она может:

```
optimized code
      ↓
assumption failed
      ↓
deoptimization
      ↓
less optimized code
```

Поэтому производительность Java-программы может зависеть от **runtime profile**.

---

## 12. Что из этого следует для production-разработчика - ~={orange}Как оптимизировать, учитывая JIT=~

### Не делать

```
«Этот метод вызывается миллион раз,
поэтому обязательно вручную inline его».
```

Вместо этого:

```
→ сначала измерить
→ понять bottleneck
→ посмотреть profiling
→ оптимизировать
→ проверить benchmark
```

### Делать

Писать:

- небольшие методы;
- предсказуемый control flow;
- нормальные типы;
- разумные абстракции;
- простые горячие циклы;
- избегать ненужной reflection в hot path;
- не создавать огромное количество объектов без необходимости в действительно hot path.

# 13. Очень короткая шпаргалка для интервью

### C1

> **Быстрый компилятор.** Быстро компилирует hot-код и делает относительно простые оптимизации: constant folding, простое inlining, dead-code/branch/loop optimizations. Его задача — быстро получить хороший native code.

### C2

> **Агрессивный оптимизирующий компилятор.** Глубоко анализирует горячий код: aggressive inlining, escape analysis, scalar replacement, loop optimizations, elimination of bounds checks, speculative optimizations. Может использовать runtime profiling и выполнять deoptimization при нарушении предположений.

### Tiered

> **Сначала быстро C1, затем для действительно горячего кода C2.** Это баланс между startup time и peak performance.

И самая полезная цепочка для запоминания:

```
C1
│
├─ быстро
├─ simple inlining
├─ constant folding
├─ simple branches/loops
└─ быстро получить хороший код

C2
│
├─ медленнее компилируется
├─ aggressive inlining
├─ Escape Analysis
├─ Scalar Replacement
├─ loop optimizations
├─ bounds-check elimination
├─ speculative optimization
└─ deoptimization
```

**А для разработчика главный вывод:** не пытайся вручную делать работу JIT. Пиши понятный код, измеряй реальные bottleneck'и и помни, что **горячий CPU-bound код после прогрева может выглядеть совсем иначе на уровне машинного кода, чем твой исходный Java-код**.
