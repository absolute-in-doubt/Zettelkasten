Q: Расскажи про checked & unchecked exceptions.
A:    
	
| Аспект                  | Checked Exceptions                                   | Unchecked Exceptions                                       |
| ----------------------- | ---------------------------------------------------- | ---------------------------------------------------------- |
| **Наследование**        | Подклассы `Exception` (не `RuntimeException`)        | Подклассы `RuntimeException` или `Error`                   |
| **Проверка**            | Компилятор требует обработку (try-catch или throws)​ | Не проверяются компилятором ​                              |
| **Время возникновения** | Compile-time (предсказуемые внешние факторы)         | Runtime (ошибки программирования) ​                        |
| **Примеры**             | `IOException`, `SQLException`                        | `NullPointerException`, `ArrayIndexOutOfBoundsException` ​ |
| **Обработка**           | Обязательна для вызова API                           | Опциональна (рекомендуется избегать) ​                     |
	
---
**Когда использовать**
	
- **Checked**: Внешние факторы вне контроля программы (файлы, сеть, БД). Позволяют восстановиться: "файл не найден — создайте новый".​
    
- **Unchecked**: Баги в коде (деление на 0, null-доступ). Их цель — обнаружить и исправить во время разработки, а не обрабатывать в продакшене

Q: Обязан ли абстрактный класс явно реализовывать методы интерфейса, который он реализует? (В виде abstract methods или в виде методов с реализацией)
A:    
Абстрактный класс, реализующий интерфейс (`implements`), **может оставить методы интерфейса абстрактными** — без реализации. Обязанность реализовать все методы переходит к **конкретным (неабстрактным) подклассам**
	
---
**Пример:**
	
```java
interface Flyable {
    void fly();  // Метод интерфейса
}
	
abstract class Bird implements Flyable {
    // НЕ реализует fly() — оставляет абстрактным
    // Компилятор не ругается!
}
	
class Eagle extends Bird {
    @Override
    public void fly() {  // ТОЛЬКО здесь обязательна реализация
        System.out.println("Eagle flies high");
    }
}
```
	
**Сравнение обязанностей**
	
| Тип класса            | implements интерфейс   | Обязан реализовать ВСЕ методы?        |
| --------------------- | ---------------------- | ------------------------------------- |
| **Обычный класс**     | ✅ `implements Flyable` | **ДА** — все методы                   |
| **Абстрактный класс** | ✅ `implements Flyable` | **НЕТ** — может оставить абстрактными |
	
**Почему так работает**
	
- Интерфейс = **контракт** (декларации методов).
    
- Абстрактный класс = **частичный шаблон** (может реализовать часть контракта).
    
- Только **финальные классы** полностью выполняют контракт.

Q: Чем отличаются StringBuilder и StringBuffer?
A: StringBuilder и StringBuffer в Java — это изменяемые классы для эффективной работы со строками, в отличие от неизменяемого String. Главное отличие: StringBuffer потокобезопасен (синхронизирован), а StringBuilder — нет и быстрее.
	
---
**Потокобезопасность**
	
StringBuffer использует синхронизацию методов (synchronized), что предотвращает конфликты при многопоточном доступе, но снижает производительность.  
StringBuilder не синхронизирован, поэтому подходит для однопоточных приложений и работает быстрее.
	
---
**Производительность**
	
StringBuilder обычно в 1,5–2 раза быстрее StringBuffer из-за отсутствия накладных расходов на синхронизацию.  
Оба класса имеют одинаковый API (append, insert, delete и т.д.) и используются для конкатенации строк в циклах.

Q: Чем отличаются `git reset` и `git revert`?
A: reset переписывает историю коммитов, а revert сохраняет.
	
---
**Git Reset**
	
Перемещает указатель ветки (HEAD) на указанный коммит, удаляя или изменяя историю после него.  
Доступны режимы:
	
| Команда                      | HEAD           | Staging Area                                 | Working Directory |
| ---------------------------- | -------------- | -------------------------------------------- | ----------------- |
| `git reset --soft <commit>`  | ← перемещается | **НЕ трогается** (изменения остаются staged) | НЕ трогается      |
| `git reset --mixed <commit>` | ← перемещается | **Сбрасывается** (unstage всех изменений)    | НЕ трогается      |
| `git reset --hard <commit>`  | ← перемещается | Сбрасывается                                 | **Сбрасывается**  |
	
---
**Git Revert**
	
Создаёт новый коммит, который отменяет изменения указанного коммита, не трогая историю.  
Безопасен для командной работы и опубликованных веток, так как история остаётся полной и линейной.  
Идеален для исправления ошибок в уже запушенных коммитах.

Q:  Для чего используется epsilon gc?
A:     
-  Это экспериментальный сборщик мусора, введённый в Java 11, который не освобождает память, а только выделяет её, пока не возникнет OutOfMemoryError. Он обеспечивает минимальный overhead на GC, полностью исключая паузы от сборки мусора.​
	
**Основные применения**
	
- Тестирование производительности: позволяет измерить скорость приложения без влияния GC.​
    
- Оценка memory pressure: показывает объём выделяемой памяти без очистки.
    
- Короткоживущие задачи: идеален для программ, завершающихся до исчерпания heap (например, скрипты).
	
- `-XX:+UseEpsilonGC`.

Q: Чем @Controller и @Repository отличаются от @Component?

Отвечает за обработку HTTP-запросов в веб-слое (Spring MVC).
	
- Распознаётся `DispatcherServlet` для маппинга методов с `@RequestMapping`.

- Поддерживает транзакции и интеграцию с `JdbcTemplate`, JPA
	
| Аннотация     | Слой        | Доп. функциональность    |
| ------------- | ----------- | ------------------------ |
| `@Component`  | Любой       | Базовая: авто-детект, DI |
| `@Controller` | Web         | Маппинг запросов         |
| `@Repository` | Persistence | Обработка исключений БД  |

Q: Какие есть поля у аннотации @Transactional и для чего они нужны?
A:       
	
| Поле                            | Тип                  | Описание                                                                                                  |
| ------------------------------- | -------------------- | --------------------------------------------------------------------------------------------------------- |
| `value` / `transactionManager`  | `String`             | Имя TransactionManager (по умолчанию "transactionManager").​                                              |
| `propagation`                   | `Propagation`        | Распространение: `REQUIRED` (поумолчанию), `REQUIRES_NEW`, `NESTED`, `SUPPORTS` и др.​                    |
| `isolation`                     | `Isolation`          | Уровень изоляции: `DEFAULT`, `READ_COMMITTED`, `SERIALIZABLE` (действует для `REQUIRED`/`REQUIRES_NEW`).​ |
| `timeout` / `timeoutString`     | `int` / `String`     | Таймаут в секундах (0=безлимит).​                                                                         |
| `readOnly`                      | `boolean`            | Только чтение (`false` по умолчанию). `readOnly=true` - оптимизация для SELECT.​                          |
| `rollbackFor` / `noRollbackFor` | `Class<Throwable>[]` | Исключения для отката/неотката (по умолчанию `RuntimeException`, `Error`).​                               |
<!--ID: 1773745478392-->


A:  `propagation` в `@Transactional` определяет, как метод участвует в транзакции:
	
- `REQUIRED` — использовать текущую транзакцию или создать новую.
    
- `REQUIRES_NEW` — всегда создавать новую, текущую приостанавливается.
    
- `MANDATORY` — метод должен вызываться внутри существующей транзакции.
    
- `SUPPORTS` — использовать текущую транзакцию, если она есть.
    
- `NOT_SUPPORTED` — выполнять без транзакции.
    
- `NEVER` — запрет на выполнение внутри транзакции.
    
- `NESTED` — вложенная транзакция через savepoint внутри текущей.

**Pattern matching for instanceof** — расширение оператора `instanceof`, которое **автоматически создает и приводит переменную** при успешной проверке типа. **НЕ новый оператор**, а **улучшение синтаксиса instanceof**.

```java
    System.out.println(s.length());
}
```
	
**Java 16+ (Pattern Matching)**
	
```java
if (obj instanceof String s) {  // ✅ Авто-приведение
    System.out.println(s.length());
}
```

Q: Чем использование JdbcTemplate лучше прямого использования JDBC?
A: **JdbcTemplate значительно лучше прямого JDBC** за счет автоматизации boilerplate-кода и устранения типичных ошибок.
	
**Основные преимущества**
	
|Проблема в чистом JDBC|Решение JdbcTemplate|
|---|---|
|`Connection conn = DriverManager.getConnection()`|Авто-получение из DataSource|
|`try-finally` для `close()` каждого ресурса|**Автоматическое управление ресурсами** (try-with-resources внутри)|
|`SQLException` (проверяемое)|**RuntimeException** (`DataAccessException`) с детализацией|
|Ручной парсинг `ResultSet`|`query().map(row -> new User(...))`|
|Повторяющийся код для каждого запроса|Один метод на запрос|
	
---
**Что НЕ оптимизирует JdbcTemplate**
	
- Не переписывает ваш SQL (нет батчинга, переиндексации)
    
- Не анализирует планы запросов
    
- Не применяет кэширование на уровне SQL
    
- **Производительность = чистому JDBC** (миллисекунды не потеряны)

Q: Расскажи как работает git и в чем его приемущества по сравнению с аналогами.
A: **Git под капотом:**
	
- Git хранит не изменения строк, а **снимки (snapshots)** всего проекта.
- Каждый коммит — это объект с:
    - ссылкой на корневое дерево файлов (tree),
    - автором,
    - сообщением,
    - ссылками на родительские коммиты.
        
- Все объекты (blob, tree, commit, tag) адресуются по **SHA-хешу**.
- Ветки — это просто **указатели на коммит**. Переключение ветки = перемещение указателя.
- История образует **направленный ациклический граф (DAG)** коммитов.
    
**Почему Git быстрый?**
	
- Большинство операций работает только с локальной БД `.git`.
- Не нужно обращаться к серверу для просмотра истории, создания веток, коммитов и слияний.
- Ветка занимает буквально несколько байт (ссылка на коммит).
    
**Почему лучше многих аналогов (SVN, CVS)?**
	
- Полная история у каждого разработчика.
- Нет единой точки отказа.
- Дешёвые ветки и быстрые merge.
- Целостность данных гарантируется хешами: подменить коммит незаметно нельзя.
- Объектная модель (commit/tree/blob) проще и гибче централизованных систем.
    
**Запомнить:**
	
> Git — это локальная база данных объектов, связанных хешами в DAG; ветка — просто указатель на коммит. Именно поэтому Git быстрый и удобный для параллельной разработки.

Q: Чем отличаются git pull от git fetch?
A: **`git fetch`**
	
- Скачивает изменения с удалённого репозитория.
    
- **Не меняет** текущую ветку и файлы.
    
- Только обновляет удалённые ссылки (`origin/main` и т.д.).
    
	
**`git pull`**
	
- Делает `fetch` + сразу интегрирует изменения в текущую ветку (`merge` или `rebase`).
    
- Может изменить рабочие файлы и вызвать конфликты.
    
	
> `fetch` — «посмотреть, что изменилось».  
> `pull` — «скачать и применить изменения».

Q: расскажи про git flow.
A: **Git Flow** — стратегия работы с ветками в Git.
	
**Основные ветки**
	
- **main (master)** — стабильный код в продакшене.
    
- **develop** — основная ветка разработки.
    
**Вспомогательные ветки**
	
- **feature/*** — разработка новой функциональности.
    
    - Создаётся от `develop`.
        
    - После завершения вливается обратно в `develop`.
        
- **release/*** — подготовка релиза.
    
    - Создаётся от `develop`.
        
    - После тестирования вливается в `main` и `develop`.
        
- **hotfix/*** — срочное исправление продакшена.
    
    - Создаётся от `main`.
        
    - После исправления вливается в `main` и `develop`.
        
	
**Схема**
	
```text
main
 ├── hotfix/*
 │
develop
 ├── feature/*
 ├── feature/*
 └── release/*
```
	
**Плюсы**
	
- Чёткое разделение разработки и продакшена.
    
- Удобно для больших команд и редких релизов.
    
**Минусы**
	
- Много веток и merge'ей.
    
- Избыточен для небольших проектов и CI/CD.
    
**Запомнить:**
	
> `main` — прод, `develop` — разработка, `feature` — фича, `release` — релиз, `hotfix` — срочный фикс.

Q: что такое boxing и unboxing?
A: **Boxing (autoboxing)** — автоматическое преобразование примитива в объект-обёртку.
	
```java
int x = 10;
Integer y = x; // boxing
```
	
**Unboxing** — автоматическое преобразование объекта-обёртки в примитив.
	
```java
Integer y = 10;
int x = y; // unboxing
```
	
**Зачем нужны обёртки?**
	
- Дженерики работают только с объектами:
    
```java
List<Integer> list = new ArrayList<>();
```
	
- Можно хранить `null`.
    
**Опасность:**
	
```java
Integer x = null;
int y = x; // NullPointerException
```
	
**Запомнить:**
	
> Boxing: `int → Integer`  
> Unboxing: `Integer → int`  
> Выполняются автоматически компилятором.
	
**Примеры:**
	
**1. Добавление примитивов в коллекции**
	
```java
List<Integer> numbers = new ArrayList<>();numbers.add(10); // autoboxing: int -> Integer
```
	
Самый частый случай.
	
---
**2. Получение значения из коллекции**
	
```java
Integer value = numbers.get(0);int x = value; // unboxing
```
	
---
	
**3. Сравнение с примитивом**
	
```java
Integer x = 100;if (x == 100) { // unboxing    ...}
```
	
Компилятор преобразует `x` в `int`.
	
---
**4. Арифметические операции**
	
```java
Integer a = 10;Integer b = 20;int sum = a + b; // оба unboxing
```
	
На самом деле:
	
```java
int sum = a.intValue() + b.intValue();
```

Q: Что такое маркерный интерфейс?
A: Маркерный интерфейс - это интерфейс без методов и констант, который служит «меткой» для класса. По этой метке компилятор, JVM или библиотечный код может определить, поддерживает ли объект определённую возможность.
	
Примеры:
	
`java.io.Serializable` — наиболее известный маркерный интерфейс:
	
```java
import java.io.Serializable;
	
public class UserSession implements Serializable {
    private String username;
}
```
	
Реализация `Serializable` указывает механизмам Java, что объект разрешено сериализовать:
	
```java
ObjectOutputStream output =
        new ObjectOutputStream(new FileOutputStream("session.bin"));
	
output.writeObject(new UserSession());
```
	
Если передать объект, не реализующий `Serializable`, будет выброшено `NotSerializableException`.
	
При этом сериализация имеет дополнительные правила: например, поля должны быть сериализуемыми либо помечены `transient`.
	
---
`java.lang.Cloneable` сообщает методу `Object.clone()`, что поверхностное клонирование объекта разрешено:
	
```java
public class Account implements Cloneable {
    private int balance;
	
    @Override
    public Account clone() {
        try {
            return (Account) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }
}
```
	
Без `Cloneable` вызов `super.clone()` приводит к `CloneNotSupportedException`.
	
Однако `Cloneable` не считается особенно удачным современным API:
	
- клонирование выполняется поверхностно;
    
- вложенные изменяемые объекты не копируются автоматически;
    
- контракт `clone()` неудобен;
    
- возможны ошибки с `final`-полями и наследованием.
    
На практике часто предпочтительнее копирующий конструктор:
	
```java
public Account(Account source) {
    this.balance = source.balance;
}
```

`java.util.RandomAccess` — маркер для списков, поддерживающих эффективный произвольный доступ по индексу:
	
```java
List<Integer> list = new ArrayList<>();
	
if (list instanceof RandomAccess) {
    // Можно рассчитывать на быстрый list.get(i)
}
```
	
`ArrayList` реализует `RandomAccess`, а `LinkedList` — нет. Библиотеки Java могут выбирать разные алгоритмы обработки списка в зависимости от этой метки.

Q: В чем разница между Collections.synchronizedMap() и ConcurrentHashMap?
A: `Collections.synchronizedMap()` — это обычная `Map`, обёрнутая общим монитором. `ConcurrentHashMap` изначально спроектирован для конкурентного доступа и обычно обеспечивает значительно лучшую масштабируемость при работе нескольких потоков.
	
Методы `Collections.synchronizedMap()` синхронизируются на одном общем объекте. Поэтому одновременно с map фактически работает только один поток.
	
**Итерация**
	
Для `synchronizedMap` синхронизации отдельных методов недостаточно. Итерация состоит из нескольких шагов, поэтому её нужно защищать вручную:
	
```java
Map<String, Integer> map =
        Collections.synchronizedMap(new HashMap<>());
	
synchronized (map) {
    for (Map.Entry<String, Integer> entry : map.entrySet()) {
        System.out.println(entry);
    }
}
```
	
Без `synchronized (map)` другой поток может изменить коллекцию во время обхода, и итератор может выбросить `ConcurrentModificationException`. Документация Java прямо требует синхронизировать доступ к collection views при итерации.
	
В `ConcurrentHashMap` итераторы являются weakly consistent: они не создают полноценный snapshot, могут отражать часть изменений, произошедших во время обхода, но не выбрасывают `ConcurrentModificationException` из-за таких изменений:
	
```java
ConcurrentHashMap<String, Integer> map =
        new ConcurrentHashMap<>();
	
for (Map.Entry<String, Integer> entry : map.entrySet()) {
    System.out.println(entry);
}
```
	
---
**Compound-операции**
	
Проблема есть не только в отдельных `get()` и `put()`, а в последовательностях операций.
	
Потенциально небезопасный вариант:
	
```java
if (!map.containsKey(key)) {
    map.put(key, value);
}
```
	
Даже если отдельные вызовы потокобезопасны, последовательность «проверить и добавить» не является атомарной: два потока могут одновременно не найти ключ и оба вызвать `put`.
	
С `ConcurrentHashMap` следует использовать специальные методы:
	
```java
ConcurrentHashMap<String, Integer> map =
        new ConcurrentHashMap<>();
	
map.putIfAbsent("counter", 0);
	
map.compute("counter", (key, oldValue) ->
        oldValue == null ? 1 : oldValue + 1);
        
ConcurrentHashMap<String, User> cache =
        new ConcurrentHashMap<>();
	
User user = cache.computeIfAbsent(userId, id -> loadUser(id));
```
	
---
**Что выбрать**
	
Используйте `ConcurrentHashMap`, если:
	
- map одновременно читают и изменяют несколько потоков;
    
- важна производительность при конкуренции;
    
- нужны `computeIfAbsent`, `merge`, `putIfAbsent`;
    
- не нужны `null`-ключи и `null`-значения;
    
- нужна безопасная итерация без обязательной блокировки всей map.
    
	
Используйте `Collections.synchronizedMap()`, если:
	
- уже есть конкретная реализация `Map`, которую нужно обернуть;
    
- конкуренция небольшая;
    
- нужна простая синхронизация всей коллекции;
    
- важно сохранить поведение или порядок исходной map;
    
- требуется поддержка `null`, которую предоставляет backing map.

Q: Что такое ThreadLocal?
A: **ThreadLocal** в Java — обертка для хранения **thread-local переменных**: каждый поток видит **свою изолированную копию** значения, без синхронизации.
	
Даёт возможность создавать static переменные, которые будут хранить значение уникальное для этого потока, таким образом, если класс используется в двух потоках, в этой static переменной будет свое значение для каждого потока и не будет race conditions.

Q: Какие могут быть проблемы при использовании ThreadLocal в реактивных системах?
A:  `ThreadLocal` плохо подходит для reactive, потому что reactive pipeline может переключаться между потоками. Значение ThreadLocal при этом теряется или может случайно протечь в другой execution.
	
В Reactor обычно используют **Reactor Context**:
	
```java
return Mono.just("data")
    .contextWrite(ctx -> ctx.put("userId", userId))
    .flatMap(x ->
        Mono.deferContextual(ctx -> {
            String userId = ctx.get("userId");
            return ...;
        })
    );
```
	
`Context` привязан не к `Thread`, а к **reactive execution/subscription**.
	
---
**Проблемы, возникающие при использовании ThreadLocal в реактивной среде:**
	
- **Thread hopping**
    
    ```
    Request A
       ↓
    Thread-1 → Thread-2 → Thread-5
    ```
    
    `ThreadLocal` теряется при переходе между потоками.
    
- **Thread pool reuse**
    
    ```
    Request A → Thread-1
                   ↓
               ThreadLocal=A
                   ↓
               pool
                   ↓
    Request B → Thread-1
                   ↓
               ThreadLocal=A  ← stale data
    ```

Q: Какие знаешь виды JIT?
A:    
- **C1 (Client Compiler)** — быстрый JIT-компилятор, небольшие накладные расходы, делает относительно простые оптимизации.
    
- **C2 (Server Compiler)** — более тяжёлый, но выполняет агрессивные оптимизации: inlining, escape analysis, loop optimizations и т.д.
    
- **Tiered Compilation** — комбинация C1 + C2. Обычно современная JVM работает именно так:
    
    ```text
    Bytecode
        ↓
    Interpreter
        ↓
    C1 → быстрый JIT
        ↓
    C2 → глубокая оптимизация горячего кода
    ```
    
	
---
**В современных JDK**
	
Основные варианты:
	
- **HotSpot C1/C2** — стандартный вариант OpenJDK.
    
- **Graal JIT** — альтернативный высокоуровневый JIT-компилятор; может использоваться как замена C2 в соответствующих конфигурациях JVM.
    
> В HotSpot есть C1 и C2. C1 быстро компилирует код с базовыми оптимизациями, C2 дольше компилирует, но выполняет более глубокие оптимизации. В режиме Tiered Compilation они работают вместе.

Q: Что такое AOT?
A: **AOT (Ahead-Of-Time compilation)** — это компиляция кода **до запуска программы**.
	
```text
Обычная JVM:
	
Java → bytecode → JVM → JIT → native machine code
                         ↑
                    во время работы
	
AOT:
	
Java → native machine code
       ↑
   до запуска
```
	
| JIT                                              | AOT                                         |
| ------------------------------------------------ | ------------------------------------------- |
| Компилирует во время выполнения                  | Компилирует до запуска                      |
| Может анализировать реальное поведение программы | Не видит runtime-поведение                  |
| Может делать runtime-оптимизации                 | Меньше возможностей для runtime-оптимизаций |
| Есть warm-up                                     | Практически нет JIT warm-up                 |
| Компиляция потребляет CPU во время работы        | Компиляция происходит заранее               |
	
**Пример:**
	
Классический пример современного AOT — **GraalVM Native Image**:
	
```text
Java/Spring application
        ↓
   Native Image
        ↓
     binary
        ↓
    запуск
```
	
Получается нативный executable, которому **не нужна полноценная JVM для запуска**.
	
Это особенно полезно для:
	
- быстрых startup time;
    
- serverless;
    
- контейнеров;
    
- приложений, где важны небольшие memory footprint и latency на старте.
    
Но есть компромисс: **JIT может оптимизировать программу на основе реального поведения во время работы**, поэтому для долгоживущих приложений JIT зачастую имеет преимущества.
	
> AOT компилирует приложение в машинный код до запуска, а JIT делает это во время выполнения. AOT даёт быстрый startup и меньше runtime overhead, а JIT может использовать информацию о фактическом поведении программы для более агрессивных оптимизаций.

Q: Какой GC подойдет, если нужна минимальная задержка/максимальная пропускная способность/баланс
A:  
**Для минимальной задержки (latency):**
	
Пример: высоконагруженный API/торговая система, где важнее, чтобы каждый запрос укладывался, например, в `10–20 ms`, чем максимальная общая производительность CPU.
	
- ZGC, поскольку у него очень короткие паузы (менее 1-10 мс). Но есть ограничение по heap (от 8 МБ до 16 ТБ).
- Или Sheennandoah GC - паузы тоже менее 10 мс (чуть больше в среднем), но не зависят от размера кучи.
	
---
**Для максимальной пропускной способности:**
	
Пример: batch-обработка миллионов записей/ETL, где допустимы длинные паузы, но важно обработать **максимум данных за единицу времени**.
	
- Parallel GC - лучший throughput, несколько потоков, минимум накладных расходов.
	
---
**Баланс:**
	
Пример: обычный backend-сервис с большим heap, где одновременно важны и приемлемые latency, и хороший общий throughput, например REST-сервис интернет-магазина.
	
- G1 GC - хороший баланс, но ниже throughput, чем у Prallel GC
	
---
**Почему длинная пауза не всегда противоречит throughput**
	
Условно:
	
```text
Parallel GC:
99% времени → приложение работает
1% → длинная GC-пауза
        ↓
высокий общий throughput
```
	
Если приложение **batch-oriented**, пауза сама по себе не страшна: пользователь не ждёт ответа в этот момент.
	
А для latency-sensitive приложения:
	
```text
ZGC:
GC работает преимущественно concurrent
        ↓
короткие Stop-The-World паузы
        ↓
стабильное время ответа
```

Q: Можно ли создать singleton одного типа дважды?
