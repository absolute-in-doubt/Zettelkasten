# enitity id - JOOQ

Расскажи, как  работает присвоение id при сохранении новой  сущности (как задается id)? В JPA при использовании SequenceGenerator один раз подтягивалось значение sequence и потом из этого батча выдавались значения.

А в JOOQ я увидел такой подход:


Тут все заполняется на уровне базы. Мне кажется, что такой подход менее эффективен, поскольку будет вызывать больше блокировок на самой sequence при параллельном создании и вообще будет намного чаще дергать sequence (пусть и не отправляя ответ по tcp)


### JOOQ устанавливает id через Sequence на уровне базы данных

```yaml
- createSequence:
    sequenceName: exchange_rate_seq
    startValue: 1
    incrementBy: 1

- createTable:
    tableName: exchange_rates
    columns:
      - column:
          name: id
          type: BIGINT
          defaultValueComputed: nextval('exchange_rate_seq')
          constraints:
            primaryKey: true
            primaryKeyName: pk_exchange_rates
            nullable: false
```


- **Легковесные блокировки:** Функция `nextval` использует атомарные операции и специальные легковесные механизмы синхронизации (latches), а не тяжелые блокировки строк или таблиц. Параллельные транзакции не выстраиваются в долгую очередь из-за сиквенса.
    
      
    
- **Серверное кэширование (`CACHE`):** Чтобы избежать лишнего дискового ввода-вывода, у последовательности в БД почти всегда задается параметр кэша (например, `CACHE 50`). В этом случае пачка значений хранится прямо в оперативной памяти СУБД (shared memory), и вызовы `nextval` происходят мгновенно.

> [!note]
> Параметр шага (`INCREMENT BY`) и параметр кэша (`CACHE`) — это **две совершенно независимые настройки** последовательности (sequence) в реляционных базах данных.
>
>- **`INCREMENT BY 1`** определяет _шаг приращения_. То есть каждое новое значение будет больше предыдущего ровно на 1 (1, 2, 3, 4 и т.д.).
>    
>- **`CACHE 50`** (если задан явно) указывает базе данных предварительно выделить и держать в оперативной памяти блок из 50 значений.
>
> Соотвтетственно при работе с sequence с шагом 1 и кэшем 50:
> 1. База данных «резервирует» в памяти сразу пачку чисел (например, с 1 по 50).
   > 
>2. Когда срабатывает `nextval('exchange_rate_seq')` (даже при каждой вставке из jOOQ/Liquibase), СУБД **не ходит каждый раз на диск** или в системный журнал (WAL) для изменения метаданных сиквенса. Она мгновенно отдает число из оперативки.
>
>3. Только когда запрашивается 51-е значение, база обновляет метаданные на диске и подтягивает в память следующий блок (начиная с 51 по 100). 

    
**Summary:** 
	_Да, при таком подходе на каждый INSERT новой сущности в базе идет внутренний запрос к sequence. Но благодаря оптимизациям (CAS операциям) - там нет долгих блокировок_ и есть локальный кэш результатов sequence как это было в самом приложении при использовании JPA._
    


### Сравнение с подходом JPA (Hibernate)

В JPA с `SequenceGenerator` и `allocationSize` (по умолчанию часто 50) применяется **клиентское кэширование**:

- Приложение один раз вызывает `nextval` и забирает пачку ID (например, 1–50) в оперативную память JVM.
    
- Следующие 49 сущностей сохраняются вообще без обращения к сиквенсу на уровне базы.
    
- **Главный минус JPA:** Если приложение аварийно перезапустится или упадет, неиспользованные ID из текущего пула пропадут навсегда, из-за чего в нумерации появятся большие «дыры». Если инстансов приложения несколько, у каждого будет свой пул, что еще сильнее увеличит разброс.    


### Почему в миграциях (Liquibase / jOOQ) выбирают `defaultValueComputed`

Такая конфигурация  переносит ответственность за генерацию ID полностью на СУБД. Это дает важные преимущества:

- **Универсальность:** Записи в таблицу может делать не только ваше Java-приложение с Hibernate, но и сторонние сервисы, скрипты миграций, аналитические инструменты или утилиты из консоли базы данных, не заботясь о клиентских пулах ID.
    
- **Предсказуемость:** Отсутствие рассинхронизации между состоянием кэша в памяти конкретного инстанса приложения и реальным состоянием базы данных.
