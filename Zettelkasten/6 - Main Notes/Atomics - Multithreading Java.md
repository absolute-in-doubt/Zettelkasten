# Atomics - Multithreading Java

`java.util.concurrent.atomic`

Атомики в Java работают как операции, которые гарантируют атомарность и видимость изменений в разделяемых переменных для многопоточных программ. 

Атомарные операции гарантируют, что операция будет выполнена полностью и никакой другой поток не сможет изменить значение переменной до завершения операции.

**~={red}Атомики не используют блокировки=~**. **Они обеспечивают атомарность через CAS — специальную атомарную инструкцию процессора, которая позволяет обновить значение, только если его никто не изменил между чтением и записью.**

> [!tip] **Что такое CAS?**
> (Compare And Swap): сравнил и, если версия больше, заменил.

### CAS (Compare-And-Swap)

CAS — атомарная операция вида:

```
CAS(address, expected, newValue)

1. Прочитать значение по address
2. Сравнить с expected
3. Если == expected → записать newValue
4. Иначе → ничего не менять
```

Например:

```java
AtomicInteger x = new AtomicInteger(10);

x.compareAndSet(10, 20);
```

#### ~={red}Все атомики заточены под `comapreAndSet(expectedValue, newValue)`:=~

Для `incrementAndGet()` значение для сравнения **берётся из текущего значения `AtomicInteger`**, но важный нюанс: Java обычно реализует это через **цикл CAS**.

Упрощённо:

```java
public int incrementAndGet() {
    while (true) {
        int current = get();          // прочитать текущее значение
        int next = current + 1;

        if (compareAndSet(current, next))
            return next;
    }
}
```


~={orange}**То есть по сути почти все операции атомиков на уровне Java сводятся к compareAndSet()*.=~

Но **не все операции атомиков буквально реализованы через `compareAndSet()`**:

- `get()` → просто атомарное чтение `volatile`-поля.
- `set()` → volatile-запись.
- `compareAndSet()` → атомарный CAS.
- `incrementAndGet()`, `addAndGet()`, `updateAndGet()` → обычно CAS-loop или соответствующая низкоуровневая атомарная операция.
- Некоторые операции могут использовать более специализированные **CPU-инструкции** напрямую.

### Почему атомарно, даже между ядрами?

Ключевой момент: **CAS — не просто несколько инструкций, объединённых в одну.**

Процессор предоставляет специальную **атомарную read-modify-write операцию** (например, `CMPXCHG` на x86).

Упрощённо:

```
CPU Core 1                  CPU Core 2
   │                           │
   │ CAS(x, 10 → 20)           │
   │                           │ CAS(x, 10 → 30)
   ▼                           ▼
┌─────────────────────────────────────┐
│ Cache Coherence / Memory System      │
│                                     │
│  эксклюзивный доступ к cache line   │
└─────────────────────────────────────┘
```

Когда Core 1 выполняет атомарный CAS:

1. Процессор получает **эксклюзивное владение cache line**, содержащей `x` (через протокол когерентности кэшей, например MESI).
2. Другие ядра не могут одновременно успешно изменить эту же cache line.
3. CPU **атомарно** выполняет:
    
    ```
    read → compare → conditional write
    ```
    
4. Если другой Core уже изменил значение, CAS увидит новое значение и **провалится**.
5. После операции cache coherence обеспечивает согласованность копий cache line между ядрами.

То есть другой поток **может одновременно попытаться выполнить CAS**, но не может «вклиниться» между `compare` и `write` первого CAS.

### Важное уточнение

Не обязательно происходит буквальная блокировка всей памяти/шины. На современных CPU атомарность обычно обеспечивается механизмами **cache coherence + специальной атомарной инструкцией**.

**Для конспекта:**

> **CAS = атомарный Compare → Conditional Write.** Процессор гарантирует неделимость этой операции даже между ядрами: cache-coherence протокол обеспечивает эксклюзивный доступ к cache line на время атомарного RMW. Поэтому другой поток либо увидит старое значение и его CAS успешно изменит, либо увидит уже изменённое значение и его CAS провалится.
